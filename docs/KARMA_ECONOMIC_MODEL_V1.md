# Karma Economic Model V1

> 目标：用**可自动执行的机制**驱动增长与安全运行，而不是靠运营堆人。  
> 用户画像：高频重度 AI 用户（愿授额度）+ 商家/企业（要安全与增效）+ 专业开发者（定制供给）。  
> 成功公式：`开发者解决的真问题 × 可授信场景 → 用户量 → 结算量 → 生态分成`

---

## 0. 一句话

**Karma = Agent 经济的非托管清算与验真层。**  
钱在主人钱包/锁仓里；协议只做：授权边界、验真放款、责任归属、信誉与分成。

---

## 1. 角色与价值交换

| 角色 | 付出 | 得到 |
|------|------|------|
| **主人（用户）** | 锁仓 USDC、授 Agent 额度、关键确认 | 省事；可追责履约；额度可控 |
| **商家 Agent** | 接单、履约、交证 | 增效获客；更快回款；信誉资产 |
| **企业 Agent** | 定制流程、合规约束 | 对外/对内自动化；审计可追溯 |
| **开发者** | 做垂直/企业定制 Agent | **持续成交分成**（可对账可提现） |
| **验真相关方**（物流/票务等） | 可信证明 | 验真服务费或场景分成 |
| **Karma 协议** | 清算、争议、信誉、安全 | 协议费（成交抽成） |

原则：**谁创造成交与可信履约，谁分钱；谁制造风险，谁付成本。**

---

## 2. 资金流（非托管）

```text
主人钱包
  → 锁仓（Capacity / Bill Credit）
  → 授权 Agent 额度（单笔/日/场景上限 + 确认策略）
  → 成交锁定（Voucher / Escrow bind）
  → 验真通过 → 放款给商家/企业
  → 协议费 + 开发者分成 +（可选）验真费 自动分账
  → 争议则冻结 → 仲裁/责任金路径
```

- Karma **不归集法币**、不做用户资金托管经营。  
- 操作台是主人控权面板，不是平台代管账户。

---

## 3. 费率与分成（V1 建议值）

> 可配置；下列为冷启动默认。机器按成交额自动执行。

### 3.1 协议费（Protocol Fee）

| 场景组 | 费率（成交额） | 说明 |
|--------|----------------|------|
| 日常高频（外卖/打车等） | **0.8% – 1.2%** | 薄利多销 |
| 票务/酒店 | **1.0% – 1.5%** | 验真成本略高 |
| B2B / 企业采购 | **0.5% – 1.0%** | 大单低费率 + 可企业订阅叠加 |
| API / 数字计量 | **1.5% – 2.5%** 或 按调用包月 | 小额高频 |

协议费覆盖：结算基础设施、争议处理预算、安全审计、信誉账本。

### 3.2 开发者分成（Developer Share）

从**协议费**中切出，而不是再向用户加一层税：

| 类型 | 占协议费比例 | 触发条件 |
|------|--------------|----------|
| 接入开发者（该 Agent 的发布者） | **40% – 50%** | 该 Agent 作为成交一方且 `p1_ready` |
| 推荐/分发开发者（可选） | **5% – 10%** | 有明确 referral 绑定 |
| Karma 金库 | **剩余** | 协议运营与安全 |

例：外卖成交 100 USDC，协议费 1% = 1.0；开发者拿 0.45，Karma 金库 0.55。

**绑定长期收益：** 分成随该 Agent 持续成交滚动，不靠一次性空投。  
未绑定开发者的「裸 Agent」分成归金库（激励补登记）。

### 3.3 验真成本（Verification Cost）

| 模式 | 谁付 | 建议 |
|------|------|------|
| 协议内基础验真（字段锁定、签收规则） | 含在协议费 | 不另收 |
| 外部真源（物流 API、票务验真） | 成本转嫁或场景附加 **0.1%–0.3%** | 透明展示 |
| 人工升级争议 | 败方或对半（规则预置） | 从责任金/保证金扣 |

### 3.4 企业订阅（可选叠加）

企业可买 **Seat / 场景包 / SLA**：

- 基础：按结算抽成  
- 专业：月费（含更高额度、审计导出、专属确认策略）  
- 不替代成交抽成，避免「只订不结算」空转

## 4. 授信与安全机制（用户肯放手的前提）

### 4.1 额度三维

每个 Agent 授权必须同时具备：

1. **单笔上限**  
2. **日累计上限**  
3. **场景白名单**（如仅 `food_delivery`）

再加确认策略：

- `AUTO`：额度内自动  
- `OWNER_CONFIRM`：超阈值 / 高风险必须主人点头  
- 高风险场景（金融/医疗等）**禁止**静默自动

### 4.2 保证金与责任金（商家/企业）

| 档位 | 条件 | 效果 |
|------|------|------|
| 正常 | 信誉良好、非确认少 | 标准保证金 |
| 观察 | 超时/拒单升高 | 保证金 ×1.5，发现降权 |
| 严格 | 多次违约 | 保证金 ×2.5+，强制主人确认 |
| 限制 | 严重或欺诈 | 限制接单 / 冻结结算 |

P6 已有的非确认阶梯与违约责任，应与本经济模型费率表对齐（同一套阈值）。

### 4.3 争议成本

- 开启争议：冻结未放款部分  
- 败方承担：争议处理费（固定小额或成交额 0.3% 封顶）  
- 恶意争议（高频败诉）：扣信誉 + 提高后续保证金

---

## 5. 信誉如何变成钱（必须可执行）

信誉分影响：

| 能力 | 高信誉 | 低信誉 |
|------|--------|--------|
| 发现排序 | 靠前 | 降权/靠后 |
| 保证金 | 更低 | 更高 |
| 可接额度 | 更高 | 受限 |
| 静默结算 | 更多场景可开 | 收紧 / 禁止 |
| 开发者分成加成（可选） | +5% 协议费分成 | 无 |

公开侧只暴露承诺哈希与聚合指标（与 P8 隐私模型一致）；明细密文可审计。

## 6. 增长飞轮（自动化）

```text
开发者一键接入 / 定制企业 Agent
        ↓
商家·企业供给变多（可验真可结算）
        ↓
重度 AI 用户更敢授额度（场景够用、风险可控）
        ↓
真实成交 ↑ → 协议费 ↑ → 开发者分成 ↑
        ↓
更多开发者解决真问题 → 供给再扩
```

**冷启动补贴（有退出条件）：**

| 阶段 | 动作 | 退出 |
|------|------|------|
| 0–90 天 | 选定 1 个垂直（建议外卖或打车），协议费中开发者分成提高到 **60%**；或每笔有效结算补贴开发者固定额 | 日均真实结算 ≥ N 笔且争议率 < X% |
| 补贴来源 | 金库 / 融资预算，**不印无限积分** | 达标后回到标准分成 |
| 禁止 | 用补贴伪装虚假成交 | 刷量扣分成 + 封禁 |

---

## 7. 开发者经济（生态核心）

### 7.1 谁算「开发者」

- 发布并绑定 Agent 的主体（个人/工作室）  
- 一键接入时登记 `publisher_id`  
- 企业定制项目可多开发者按贡献比例分（V1 先支持主开发者 100%）

### 7.2 结算与提现

- 分成计入开发者余额（与成交 attestation 绑定，可审计）  
- T+1 或 T+7 可提现至绑定钱包  
- 操作台可见：成交笔数、分成、争议扣减、待结算

### 7.3 激励对齐

- **只奖励有效结算**（验真通过且未恶意撤销）  
- 争议败诉按比例回扣分成  
- 长期：连续 90 天活跃开发者可获「费率优惠券」给其终端用户（促进留存）

---

## 8. Karma 金库用途（透明）

协议费净收入优先顺序：

1. 安全审计与漏洞赏金  
2. 争议坏账与误放款准备金  
3. 真源验真 API 成本  
4. 冷启动补贴（有上限）  
5. 协议研发与标准推进  

公开季度简报：成交额、费率、分成总额、争议率、准备金余额（聚合，无明文当事人）。

## 9. 与现有协议模块的映射

| 经济概念 | 现有能力锚点 |
|----------|----------------|
| 锁仓 / 额度 | Capacity + Runtime Key + automation-policy |
| 主人确认 | P4 Human Confirmation |
| 字段锁定 | P5 Important Fields |
| 接单超时 / 责任金 | P6 Accept Fulfillment |
| 交付验真 | P7 Delivery Verification |
| 结算信誉 / 加密证明 | P8 Settlement Reputation |
| 一键接入 | `POST /v1/agents/one-click-connect` |
| 操作台控权 | Console：钱包、锁仓、授权、订单、争议、收付 |

V1 工程落地优先序：

1. 成交时自动计提协议费 + 开发者分成账本  
2. 操作台「开发者收益 / 主人授权 / 商家成交」三块看板  
3. 信誉分 ↔ 发现排序 / 保证金倍率 打通（已有雏形则校准阈值）  
4. 冷启动补贴开关与退出条件配置化

## 10. 90 天试点参数（建议拍板）

| 参数 | 试点值 |
|------|--------|
| 垂直 | `food_delivery`（或 `ride_hailing`） |
| 协议费 | 1.0% |
| 开发者占协议费 | 60%（90 天后降至 45%） |
| 用户默认单笔额度 | 由主人设；产品建议 ≤ 50 USDC |
| 日累计建议 | ≤ 200 USDC |
| 商家接单 TTL | 沿用 P6（外卖 300s） |
| 争议费率 | 败方 0.3% 封顶 5 USDC |
| 成功退出补贴 | 日均 ≥ 50 笔真实结算且争议率 < 2% 连续 14 天 |

## 11. 反方压力测试（机制自检）

| 攻击 | 机制应答 |
|------|----------|
| 刷量骗分成 | 仅验真通过计费；异常地址/自成交降权；回扣分成 |
| 串通假交付 | 硬证据 + 高风险禁静默；争议冻结 |
| 短闭环截胡 | 兼容 AP2/x402，收「验真放款」费而非死磕收银台 |
| 开发者只接不维护 | 分成随持续成交；长期不活跃失去场景加权 |
| 平台被指托管 | 非托管锁仓 + 主人授权面板；公开资金流说明 |

---

## 12. 决策摘要

1. **收入**：成交抽成为主，企业订阅为辅。  
2. **分成**：协议费的约一半给开发者，绑定长期成交。  
3. **安全**：额度三维 + 场景确认 + 保证金阶梯 + 争议成本。  
4. **信誉**：直接影响排序、保证金、额度——能换钱才算资产。  
5. **增长**：开发者解决真问题 → 供给 → 授信用户 → 成交 → 分成 → 更多开发者。  
6. **冷启动**：有限额、有退出的补贴，禁止刷量。
